# Kafka 보존·미전송 복구

## 수신·전송 순서

```text
KIS 프레임 수신·파싱
→ 체결별 이벤트 ID 생성
→ 로컬 전송 대기 파일 기록·force(true)·원자적 이름 변경
→ 별도 전송 작업이 대기 순서대로 Kafka 발행
→ Kafka 성공 응답 확인
→ 해당 대기 파일 삭제

Kafka Consumer → MariaDB 트랜잭션 → QuoteStore → 화면
```

- 전송 대기 기록에는 최초 이벤트 ID·체결 값·토픽을 보관한다. 재전송할 때 새로운 ID나 수신 시각을 만들지 않는다.
- Kafka 연결이 끊겨도 디스크 기록이 가능한 동안 수집을 계속한다. 전송 작업은 실패한 첫 기록에서 멈추고 다음 실행에 재시도한다. 오래된 기록을 새 기록보다 먼저 전송한다.
- Kafka 저장 성공과 DB 반영 완료는 서로 다르다. 대기 파일은 Kafka 성공 응답 후 정리하며, DB 반영 재시도는 Kafka Consumer가 맡는다.
- Kafka가 저장했지만 성공 응답을 수집기가 받지 못하면 같은 이벤트가 재전송될 수 있다. 동일 이벤트 ID의 DB 중복 검사로 거래량 재합산을 막는다. 한 번만 전송되는 구조는 아니다.
- DB 저장 전 처리 위치 커밋 금지 규칙은 기존 영속 저장 경로를 따른다.

## 로컬 전송 대기 저장소

| 설정 | 기본값 |
| --- | --- |
| 활성화 | realtime 프로필에서 활성화 |
| 디렉터리 | 백엔드 실행 디렉터리의 `.realtime-spool` |
| 최대 기록 | 100,000건 |
| 최대 데이터 크기 | 256 MiB |
| 재시도 간격 | 전송 작업 종료 후 1초 |
| 한 실행의 전송 수 | 최대 100건 |

- `STREAM_OUTBOX_DIRECTORY`로 경로를 지정할 수 있다. 같은 실행 디렉터리·설정 경로를 유지해야 다음 실행에서 복원된다. 저장소는 Git 제외 대상이다.
- 수집기 한 프로세스만 디렉터리를 사용하도록 파일 잠금을 잡는다. 두 프로세스의 동시 사용은 시작 실패로 처리한다.
- 설정된 건수 또는 크기를 초과하면 새 수신을 중단한다. 디스크 기록·삭제 오류, 손상된 파일, 중단된 `.writing` 파일도 확인이 필요하다. 기존 파일을 자동 삭제하거나 넘기지 않는다.
- 오류로 차단된 수집기는 원인 해결 후 재시작한다. 단순 재시작만으로 손상된 기록이 복구되지는 않는다.
- 토픽 또는 수집 종목을 바꿨는데 이전 대기가 남아 있으면 전송을 차단한다. 기존 설정에서 먼저 대기를 처리하거나 별도 이관 절차를 정한다.
- 조회 API의 `pendingQuotes`는 대기 건수, `outbox`는 `READY`·`BLOCKED`·`DISABLED` 상태다. 화면에는 전송 대기 또는 저장소 확인 필요 상태를 표시한다.

## Kafka 디스크 보존

2026-11-06 실제 Docker 환경에서 Kafka에 테스트 메시지를 발행한 뒤, 같은 명명 볼륨으로 컨테이너를 재생성해 동일 메시지를 읽었다. 이미지의 Kafka 실행 계정이 쓸 수 있도록 로그 디렉터리와 볼륨 마운트 경로를 `/var/lib/kafka/data`로 지정한다.

`compose.yml`은 Kafka 로그 디렉터리를 `kafka_data` 명명 볼륨에 연결한다. 컨테이너 재시작 후에도 같은 볼륨을 사용해야 한다.

- 단일 브로커·파티션 1개·복제본 1개 구성을 유지한다.
- 기본 보존 기간은 7일이며 파티션당 보존 크기는 1 GiB이다. 기간과 크기 중 먼저 도달하는 조건에 따라 오래된 세그먼트가 정리될 수 있다.
- 세그먼트는 최대 64 MiB, 최대 1시간 단위로 분리하며 보존 조건은 1분마다 검사한다. 보존 크기는 전체 디스크 사용량의 정확한 상한이 아니다.
- 토픽에 별도 보존 설정이 있으면 브로커 기본값보다 우선할 수 있으므로 운영 전에 확인한다.
- `acks=all`·Producer 멱등 전송을 유지한다. 복제본이 하나이므로 디스크 손실이나 브로커 장비 고장까지 보호하는 구성은 아니다.

설정 근거: [Kafka 3.9 브로커 설정](https://kafka.apache.org/39/configuration/broker-configs/), [Apache Kafka 공식 Docker 예제](https://github.com/apache/kafka/blob/trunk/docker/examples/docker-compose-files/cluster/combined/plaintext/docker-compose.yml).

## 실행

프로젝트 루트에서 Kafka를 실행한 뒤 외부 Kafka 모드로 백엔드를 시작한다.

```powershell
docker compose up -d kafka
.\start-realtime.ps1 -UseExternalKafka
```

기존 Kafka를 사용 중이었다면 기존 로그 위치·볼륨·클러스터 ID와 현재 설정을 먼저 대조한다. 이 파일 변경이 기존 로그를 새 볼륨으로 이관해 주지는 않는다. 기존 볼륨이나 토픽을 초기화하면 복구에 필요한 메시지·처리 위치가 사라질 수 있다.

`-UseExternalKafka`를 생략한 내장 Kafka 실행은 개발용이다. 실행마다 브로커가 새로 생성되므로 Kafka 메시지 보존 검증에 사용할 수 없다. MariaDB 분봉과 전송 대기 파일의 복원은 가능하지만, Kafka 성공 응답 후 파일이 삭제되고 DB에 반영되기 전에 내장 브로커가 종료된 구간은 보호하지 못한다.

## 복구 범위와 제한

- 수집기 자체가 꺼져 받지 못했거나 디스크 기록 완료 전에 중단된 체결은 이 경로로 복구할 수 없다. 용량 부족 시 마지막 프레임의 미기록 체결도 외부 재조회가 필요할 수 있다.
- 한 프레임에 체결이 여러 건 있으면 체결별로 기록한다. 중간 오류 시 기록 완료된 앞부분은 보존되지만 프레임 전체를 하나의 트랜잭션으로 기록하지는 않는다.
- 파일 데이터 강제 반영과 원자적 이동을 사용한다. 전원 손실·파일시스템 메타데이터 손상까지 보장하는 저장 장치 검증은 하지 않았다.
- Kafka 보존 기간·크기를 넘긴 미처리 메시지, 디스크 손실, 외부 데이터 미수신은 별도 복구 대상이다.
- 현재 DB 집계는 마지막 시세보다 오래된 체결을 과거 봉에 추가하지 않는다. 이번 수집기의 대기 순서는 유지하지만 임의의 지연·역순 데이터 재집계는 포함하지 않는다.
- 대기 파일은 같은 수집기 디스크에 있다. 별도 수집 서버나 컨테이너로 옮길 때도 이 디렉터리를 보존·마운트해야 한다.
- Redis는 아직 연결하지 않았다.

## 검증 구분

- 임시 디렉터리에서 파일 재개방, 용량 제한, 잠금, 손상·중단 파일 처리, 재전송 ID·순서 보존을 검사한다.
- 별도 JVM을 실제 강제 종료한 뒤 대기 파일과 잠금 복구를 검사한다.
- Kafka 실패·성공 응답 유실 상황은 모의 전송기로 검사한다. 실제 Embedded Kafka로는 디스크 대기 복원 → Kafka → H2 시험 DB 분봉 반영을 확인한다.
- 사용자 DB·KIS는 이 테스트에서 사용하지 않는다. Docker 컨테이너 재시작·실제 Kafka 장시간 중단·전원 손실 테스트와는 구분한다.
