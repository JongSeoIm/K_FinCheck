# 실시간 분봉 저장·복원

로컬 MariaDB에 분봉 테이블을 적용한 상태에서 프로젝트 루트에서 실행한다.

```powershell
$env:STREAM_PERSISTENCE_ENABLED = 'true'
.\start-realtime.ps1
```

외부 Kafka를 사용하는 경우 백엔드 실행 명령에 `-UseExternalKafka`를 추가한다. 실시간 화면은 QuoteStore의 상태를 WebSocket으로 전송하며 별도 조회 캐시를 사용하지 않는다.

## 범위

- MariaDB에 1·3·5·10·15·30·60분봉과 최신 시세, 처리 이력을 저장한다.
- 진행 중인 분봉도 반영하며, 활성화한 서버가 시작할 때 종목·주기별 최근 최대 3,000개 봉을 QuoteStore에 복원한다.
- 1·5·30초봉은 이 저장 경로에서 제외한다. 기존 메모리 경로와 달리 영속 경로에서는 초봉을 생성하지 않는다.
- 이 문서는 Consumer 이후 DB 저장·복원을 다룬다. 수집기 전송 대기 저장소와 Kafka 보존 설정은 [Kafka 보존·미전송 복구](Kafka_보존_및_미전송_복구.md)를 참고한다. 원본 체결 전체의 장기 보존은 포함하지 않는다.

## 활성화 전 준비

1. 기존 MariaDB를 백업하고 `company` 테이블에 수집 대상 기업이 있는지 확인한다.
2. `database/migrations/002_realtime_persistence_draft.sql`을 검토한 뒤 해당 프로젝트 DB에 수동 적용한다.
3. 서버 실행 환경에 `STREAM_PERSISTENCE_ENABLED=true`를 설정하고 realtime 프로필로 실행한다.
4. `stream.persistence.source`가 수집 이벤트의 출처와 일치하는지 확인한다. 기본값은 `KIS_WEBSOCKET_KRX`이다.

공유 설정의 기본값은 비활성이며 자동 초기화에는 등록하지 않는다. 각 개발자는 자신의 DB에 SQL을 적용한 뒤 활성화한다.
`CREATE TABLE IF NOT EXISTS`는 기존에 잘못 생성된 테이블을 수정하지 않으므로, 과거 초안을 적용했다면 컬럼과 제약조건을 별도로 대조해야 한다.
특히 `trade_time`은 현재 QuoteEvent와 같은 `HH:mm` 또는 `HH:mm:ss` 형식이다.

## 저장 순서

```text
KIS 수신 → 프로젝트 이벤트 ID를 포함해 Kafka 발행
→ Consumer가 메시지와 Kafka 위치 확인
→ DB 트랜잭션: 중복 확인·처리 이력·모든 분봉·최신 시세 저장
→ DB 커밋 성공
→ QuoteStore에 DB에서 확정한 결과 반영
→ Listener 정상 종료 후 Kafka 처리 위치 커밋
```

- 내부 이벤트 ID는 UUID이며 Kafka 메시지 안에 포함한다. 전송 대기·재전송에서도 최초 ID를 유지한다.
- 기존 ID가 없는 Kafka 메시지는 원래 메시지 내용으로 결정적인 ID를 생성해 재처리 호환성을 유지한다.
- 동일 ID의 내용을 바꾸면 정상 중복으로 무시하지 않고 오류로 처리한다.
- 메모리에는 체결량을 다시 합산하지 않고 확정된 봉 값을 반영한다.
- DB 저장에 실패하면 트랜잭션 전체를 롤백하며 Kafka 레코드를 재시도한다. 고정 횟수 이후 메시지를 건너뛰지 않도록 설정했다.
- 이 설정에서는 잘못된 메시지도 처리를 막을 수 있다. 오류 상태 점검과 원인 해결이 필요하며 별도 격리 큐·운영 알림은 아직 없다.

## 순서·중복의 현재 제한

- 기존 QuoteStore와 동일하게 마지막 시세보다 체결 시각이 오래되거나 같은 거래일의 누적 거래량이 증가하지 않으면 집계를 건너뛴다.
- 건너뛴 이벤트도 처리 이력에는 남는다. 처리 이력의 존재가 곧 해당 체결이 봉에 합산되었다는 의미는 아니다.
- 따라서 늦게 도착한 정상 체결을 과거 봉에 다시 넣는 기능은 아직 없다. 재전송 순서 보장·지연 데이터 정책은 후속 과제다.
- 누적 거래량으로 재접속 중복을 제한하지만, 모든 KIS 재전송·시장 조건에서 정확한 식별을 보장하는 것은 아니다.
- 현재 토픽은 파티션 1개이다. 파티션·처리기 확대 전 종목별 순서·동시 갱신 테스트가 필요하다.
- Kafka 토픽을 삭제·재생성하면 동일 위치 번호가 재사용될 수 있다. 토픽과 처리 이력을 임의로 초기화하지 않는다.

## 복원과 장애 표시

- 서버 시작 시 DB 조회에 실패하면 영속 기능을 켠 서버는 시작에 실패한다. 메모리 모드로 조용히 전환하지 않는다.
- 마지막 시세와 분봉을 복원해도 수집 중단 구간을 채웠다는 뜻은 아니다. KIS 과거 조회를 통한 보충 범위는 별도로 확인해야 한다.
- 최초 수신·체결 시각을 유지하므로 재시작만으로 오래된 시세의 기준 시각이 현재로 바뀌지 않는다.
- `is_closed`는 뒤의 체결이 들어왔을 때 지난 구간을 종료 처리한다. 장 마감 후 체결이 없을 때 바로 종료 상태로 바꾸는 타이머는 아직 없다.
- Kafka 디스크 보존에는 별도 볼륨 설정과 실행 검증이 필요하다. DB 백업은 이 코드만으로 해결되지 않는다.
- `LocalRealtimeApplication`의 내장 Kafka는 실행할 때마다 새로 생성된다. 로컬 실행 그룹에는 실행별 UUID를 붙여 이전 브로커의 DB 처리 위치와 충돌하지 않도록 한다. 이는 Kafka 메시지 보존이나 장애 복구를 구현한 것이 아니다. 외부 Kafka를 쓰는 서버의 그룹 설정은 유지한다.

## 검증 구분

- H2의 MariaDB 호환 모드로 신규 SQL의 기본 구조, 저장·복원, 트랜잭션 롤백을 검사한다. H2 실행용으로 문자셋·엔진 지정만 제거한다.
- Embedded Kafka 테스트로 DB 실패 시 처리 위치 보류와 복구 후 재처리를 확인한다.
- 테스트는 사용자 MariaDB와 KIS에 연결하지 않는다. 전체 프로세스 강제 종료·실제 MariaDB 장애·Kafka 디스크 손실 검증을 대신하지 않는다.
- 실제 MariaDB 적용·활성화 후 별도의 재시작·장애 테스트가 필요하다.

## 로컬 MariaDB 확인 (2026-11-05)

- 신규 테이블 3개를 로컬 MariaDB에 수동 생성했고 비공개 로컬 설정에서 저장 기능을 활성화했다. 기존 테이블은 변경하지 않았다.
- 별도 QA 출처의 합성 체결 2건으로 7개 분봉 주기의 OHLC·거래량 저장과 동일 이벤트 재처리 시 중복 합산 방지를 확인했다.
- KIS 연결을 끈 격리 Spring 서버에서 조회 API로 복원을 확인하고, 해당 서버 프로세스를 강제 종료·재시작한 뒤 동일한 분봉과 거래량이 복원되는 것을 확인했다.
- 검증용 데이터는 제거했으며 기존 회원·기업·관심 종목·실적·대화 테이블의 행 수는 전후 동일했다.
- 실제 KIS 체결을 이용한 장중 검증, MariaDB 중단·복구, Kafka 디스크 복구는 아직 확인하지 않았다.
